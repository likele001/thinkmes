# 工作流统一后治理路线图

## 1. 背景与目标

当前系统工作流已统一到 `wf_*` 引擎体系，标准链路为：

- 路由：`app/admin/route/workflow.php`
- 控制器：`app/admin/controller/workflow/*`
- 模型：`app/admin/model/workflow/*`
- 引擎：`app/common/service/workflow/WorkflowEngine.php`
- 数据：`fa_wf_*` 表族

本路线图目标从“统一改造”调整为“统一后治理”：

1. 清理旧链路遗留与歧义入口
2. 固化统一规范，防止回退到旧实现
3. 提升可维护性、可审计性与交付一致性

## 2. 改造原则

1. **业务连续性优先**：不影响线上审批闭环
2. **统一口径不回退**：所有新增必须走 `wf_*`
3. **可观测与可回滚**：全程对账、开关化控制
4. **租户与权限不破坏**：保持现有中间件链路稳定
5. **文档先行**：每一步有决策记录与操作手册

## 3. 范围定义

### 3.1 涉及代码与脚本

- 路由：`app/admin/route/workflow.php`、`app/admin/route/app.php`
- 标准控制器：`app/admin/controller/workflow/Definition.php`、`Module.php`、`Approval.php`
- 标准模型：`app/admin/model/workflow/*.php`
- 标准引擎：`app/common/service/workflow/WorkflowEngine.php`
- 标准脚本：`database/migrate_wf_engine_linear.sql`
- 遗留清理对象：`app/admin/controller/Workflow*.php`、`app/admin/model/Workflow*.php`、历史迁移脚本与备份文件

### 3.2 不在本轮范围

- 大规模 UI 重构（仅做入口收敛）
- 非工作流业务域功能调整（MES/CRM 核心业务逻辑不改）

## 4. 三期治理计划（不停机）

## 第一期：统一口径固化（建议 1 周）

### 目标

- 固化“唯一主线为 `wf_*`”准入规则
- 禁止旧工作流入口新增功能
- 完成统一口径检查基线

### 关键动作

1. 发布治理决策：`wf_*` 为唯一运行与开发主线
2. 盘点遗留入口（路由、菜单、页面、API、SQL）
3. 增加准入检查：
  - 代码评审检查禁止引用旧工作流类
  - 新增流程仅允许 `fa_wf_*` 写入
4. 建立回归用例：
  - 发起、审批通过、驳回、转交、撤回、超时提醒

### 里程碑

- M1：统一主线决策发布并生效
- M2：遗留入口台账完成并经研发评审
- M3：准入规则上线并通过基础回归

## 第二期：遗留清理与入口收敛（建议 1-2 周）

### 目标

- 清理旧链路对外入口与干扰文件
- 保持线上流程稳定运行

### 关键动作

1. 收敛入口：
  - 菜单仅保留 `workflow/*` 新入口
  - 路由层移除旧入口映射（或设为不可达）
2. 清理遗留文件：
  - 归档 `*_old.php.bak`、`*_old.html.bak`
  - 清理无引用旧页面与旧 JS
3. 建立对账机制：
  - 实例总量、待办量、已办量、驳回量按日比对
  - 差异入库并告警
4. 完成权限节点复核：
  - 新入口权限树、角色授权与菜单可见性一致

### 里程碑

- M4：旧入口下线清单执行完成
- M5：遗留文件归档完成
- M6：对账稳定且权限联调通过

## 第三期：规范固化与持续治理（建议 1 周）

### 目标

- 防止后续版本回退到旧实现
- 建立可持续治理机制

### 关键动作

1. 发布《工作流接入规范（wf）》，纳入研发基线
2. 新增流程模板统一使用 `wf_*` 脚手架
3. 在 CI 或脚本中加入旧类引用扫描
4. 固化数据库脚本执行序列（以 `wf` 为唯一口径）
5. 建立季度巡检（入口、权限、脚本、日志）

### 里程碑

- M7：统一规范发布并纳入研发流程
- M8：自动化扫描上线并稳定运行
- M9：季度巡检机制正式执行

## 5. 风险与应对

### 5.1 数据一致性风险

- 风险：新增代码误用旧模型/旧表导致口径漂移
- 应对：准入检查 + 代码扫描 + 日常对账

### 5.2 审批中断风险

- 风险：旧入口下线时权限或菜单配置遗漏
- 应对：分环境验证 + 回归测试 + 发布回滚方案

### 5.3 权限与菜单错配风险

- 风险：切流后权限节点未同步导致不可访问
- 应对：切流前完成权限树映射与菜单联调

### 5.4 运维执行风险

- 风险：多环境脚本顺序不一致
- 应对：建立统一执行清单、记录执行日志与版本号

## 6. 验收标准（建议）

1. 新增审批场景 100% 走 `wf_*` 链路
2. 旧链路在线入口全部下线或仅保留只读审计
3. 连续 14 天核心对账项差异在阈值内
4. 回归用例全部通过（功能 + 权限 + 租户 + 性能）
5. 统一接入文档可指导新模块独立接入

## 7. 组织与职责

## 11. 强制规范清单（PR 检查项、禁用名单、上线前脚本）

本节供研发、测试、运维直接执行：**合并前自检 + 发布后兜底**，确保不再回退到旧 `workflow_*` / `fa_workflow*`。

### 11.1 PR / Code Review 必查项

| 序号 | 检查项 | 说明 |
|------|--------|------|
| R1 | 数据表口径 | 新增或修改的读写仅允许 `fa_wf_*`（如 `wf_definition`、`wf_node`、`wf_module`、`wf_instance`、`wf_task`、`wf_log`），禁止 `fa_workflow*`、`Db::name('workflow_...')` |
| R2 | 引擎入口 | 流程发起、通过、驳回、转交、撤回须经 `app\common\service\workflow\WorkflowEngine` 或封装层 `app\admin\service\WorkflowService`，禁止自写一套状态机绕过引擎 |
| R3 | 控制器与路由 | 后台工作流页面仅走 `app/admin/controller/workflow/*` 与 `app/admin/route/workflow.php`，禁止恢复根目录 `Workflow*.php` 式旧入口 |
| R4 | 模型与命名空间 | 禁止 `use app\admin\model\Workflow*`（旧模型已移除）；业务侧仅可依赖 `app\admin\model\workflow\*` |
| R5 | SQL 与迁移 | 禁止新增依赖 `migrate_workflow_*.sql` / `migrate_workflow_simple.sql`；增量以 `migrate_wf_engine_linear.sql` 及后续 `wf` 系列为准 |
| R6 | 菜单与权限 | 新菜单 URL 必须指向 `workflow/*`，权限节点与 `auth_rule` 一致，避免旧路径残留 |
| R7 | 跨模块接入 | 新业务表须在 `wf_module` 配置绑定，审批结果回写业务状态字段，禁止硬编码节点 ID |
| R8 | 视图与 JS | 工作流相关页面放在 `app/admin/view/workflow/**`，脚本按 `public/assets/js/backend/` 约定加载，不复制旧 `workflow_approval` 等死路径 |

**合并前（提交人）**：本地执行一次 `bash scripts/pre_release_wf_check.sh`（见 11.3），无报错再提 PR。

**评审人**：对 diff 执行关键词抽查：`workflow_`（表名）、`fa_workflow`、`WorkflowDefinition`、`WorkflowInstance`（旧类）。

### 11.2 禁用名单（类、表、脚本模式）

以下视为 **违规引用**，PR 应拒绝或要求改正：

**PHP 命名与路径（禁止新增引用）**

- 旧模型类名（已删除，仅作扫描关键字）：`WorkflowDefinition`、`WorkflowInstance`、`WorkflowNode`、`WorkflowEdge`、`WorkflowModule`、`WorkflowApprovalRecord`、`WorkflowState`、`WorkflowTransition` 等位于 `app\admin\model\` 根下的旧文件
- 旧控制器风格：根命名空间 `app\admin\controller\Workflow`（非 `workflow\` 子目录）

**数据层（禁止）**

- 表名前缀：`fa_workflow%`（`information_schema` 中不应再存在；新环境以删除迁移为准）
- ThinkPHP 表别名：`Db::name('workflow_...')`、任意 `workflow_*` 逻辑表名（与 `wf_*` 混淆）

**迁移与脚本（禁止作为新依赖）**

- `database/migrate_workflow_engine.sql`
- `database/migrate_workflow_simple.sql`
- 其它仅服务旧表族的脚本（以仓库当前 `database/` 清单为准）

**允许（勿误杀）**

- `app\admin\service\WorkflowService`：对 `WorkflowEngine` 的租户/用户上下文封装，**允许使用**
- `app\common\service\workflow\WorkflowEngine`：唯一标准引擎入口
- `Db::name('wf_*')`：标准表访问方式

### 11.3 上线前检查脚本

仓库提供可执行脚本（项目根目录运行）：

```bash
bash scripts/pre_release_wf_check.sh
```

可选：检查当前连接库是否仍残留旧表（需本机可执行 `mysql` 且账号能查 `information_schema`）：

```bash
export WF_MYSQL_CMD='mysql -h127.0.0.1 -P3306 -uUSER -pPASS 数据库名'
bash scripts/pre_release_wf_check.sh
```

脚本行为摘要：

1. 扫描 `app/**/*.php`：禁止 `Db::name('workflow_*')`、`fa_workflow` 字面量、常见旧工作流模型类名
2. 若设置 `WF_MYSQL_CMD`：查询当前库是否存在 `fa_workflow%` 表，存在则失败退出

**建议在 CI 中**：每次推分支或合并前执行该脚本；与现有 `php think` / 单测并行，失败即阻断构建。
